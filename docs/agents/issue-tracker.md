# Issue tracker: GitHub

Tickets und Spezifikationen liegen ausschließlich in GitHub Issues
von `TobioBobi/secret-word-society`. Keine lokale Ticketliste führen.

Geeignete verbundene GitHub-APIs bevorzugen; alternativ `gh` verwenden.
Vor Schreibzugriffen das Zielrepository prüfen.

Vor Ticketarbeit das Issue, Kommentare, Abhängigkeiten und verknüpfte
PRs lesen. Offene Ideen und Issues sind keine Implementierungsaufträge.

Native GitHub-Unterissues und Abhängigkeiten verwenden.
Falls nicht verfügbar, `Part of #N` bzw. `Blocked by: #N` im Issue
festhalten. Erst beginnen, wenn alle Blocker geschlossen sind.

Fortschritt und fachliche Umfangsänderungen im Issue dokumentieren.
Mehrzeilige CLI-Texte über `--body-file` übergeben.

PRs nur nach ausdrücklicher Nutzerfreigabe erstellen.
Bei vollständiger Umsetzung `Closes #N` verwenden; Teilumsetzungen
nur referenzieren. Nach Merge den Issue-Abschluss verifizieren.

Öffentliche Inhalte auf geeignete Projektinformationen beschränken;
keine persönlichen Pfade, internen Links oder Werkzeugprotokolle.

## Pull requests as a triage surface

**PRs as a request surface: no.**

## Skill-Konventionen

„Publish to the issue tracker“ bedeutet: ein GitHub Issue erstellen.
„Fetch the relevant ticket“ bedeutet: das zugehörige Issue samt
Kommentaren, Abhängigkeiten und verknüpften PRs lesen.
